# Research: sidekick prompt-cache sharing

Resolves GitHub issue #4 (parent map #2). Researched 2026-10-21 against primary sources: Anthropic API and Claude Code docs, the `openai/codex` and `agentclientprotocol/*` repositories, OpenAI API docs, one first-party GitHub issue, and one local experiment.

The question: can sidekicks share a prompt cache, and in which shapes? The claims come from the exported OpenCode session `building-a-more-efficient-opinionated-alternative-to-t3-code.json`, messages 8 and 17 to 19. Those messages cite secondary write-ups (Reddit, HN, blogs). Everything below goes back to the owner of the claim.

## Verdict

Mostly right, with four corrections.

- **Confirmed:** exact-prefix semantics, TTLs of 5 minutes and 1 hour, write and read multipliers, Claude Code fork subagents reading the parent's cache on their first request, the two TTL settings, tool-definition changes busting the cache, Agent SDK session fork, and the existence of ACP `session/fork`.
- **Wrong or imprecise:**
  1. Cache scope is not "account/org". On the Claude API it is per workspace (narrower than an organization). On Bedrock and Google Cloud it is per organization. Anthropic documents no account boundary at all.
  2. Cache reads are not always 0.1x. On Opus 5.5 and Sonnet 5.5 they are 0.05x, and on Fable 5.1 and Mythos 5.1 they are 0.025x.
  3. "Batch sibling spawns in one burst so they share a cache window" fails if the siblings start at the same instant. An entry is readable only after the first response begins. Claude Code's own workflow runtime staggers siblings for this reason.
  4. The 37k, 950, 3%, 80% and 16% numbers are real but come from one developer's measurement. They are not an Anthropic figure, and they are not a general rule.
- **Not verifiable from primary sources:** why a fork keeps the Agent tool (the cache rationale), whether a Codex fork keeps the parent's cache key, whether a Codex reasoning-effort change shortens the reusable prefix, the "7 subagents eat 30% of a 5-hour window" figure, and how cache reads count against a subscription window.

One local experiment (below) shows that Claude Code forks do read most of the parent's cache. Reuse was partial in two of three forks, so budget for a partial miss.

| 10 | Use 1h for main and long-lived sidekicks, 5m for short workers | Confirmed, but the default already does this, with a catch | [Which TTL each request gets](https://code.claude.com/docs/en/prompt-caching#which-ttl-each-request-gets): on a subscription within plan usage the main conversation gets 1h and "everything else" gets 5m. "Everything else" includes subagents, workflows, teammates, **forks**, compaction and titles. With an API key or cloud provider both buckets default to 5m. A fork's cache therefore dies after 5 minutes by default, even though it shares the parent's 1h prefix. Set `subagentPromptCacheTtl` to `1h` to change that. A subagent's own `experimental.cacheTtl` frontmatter (v2.1.248 or later) sits between the setting and `ENABLE_PROMPT_CACHING_1H` in precedence. |
| 11 | Changing the tool array busts the cache | Confirmed | API docs invalidation table: "Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache". Claude Code docs: tool definitions sit in the system-prompt layer, and adding or removing a tool invalidates everything after it. When tool search defers MCP tools (the default on supported models), Claude Code keeps the first request's tool list for the whole conversation, so connecting or removing an MCP server mid-session does not bust the cache. Enabling `/advisor` is also safe. |

Fast mode adds a header that is part of the key. The API docs also say thinking configuration and `output_config.effort` invalidate message blocks. ## Local experiment: do Claude Code forks read the parent's cache?

Setup: Claude Code 2.1.306, `claude -p ... --model haiku --tools "" --output-format json`, one working directory, run on 2026-10-21. A base session, then `--resume <id> --fork-session` forks. I read `usage` from each result.

| Run | cache_creation | cache_read | Note |
|---|---|---|---|
| base (cold, new session) | 5,883 (all `ephemeral_1h`) | 3,262 | It read 3,262 tokens it never wrote, so a shared system-prompt prefix is reused across separate sessions |
| fork 1 | 3,604 | 5,582 | Reused 61% of the prefix |
| fork 2 (after fork 1 finished) | 3,604 | 5,582 | Did not read fork 1's write |
| plain `--resume` (no fork) | 3,604 | 5,582 | Same as the forks |
| fork 3 (after the resume) | 67 | 9,161 | Reused essentially the whole prefix |

What it shows:

- Forks do read the parent's cache. The first fork got 5,582 of about 9,150 tokens from cache.
- The first request after a headless `-p` resume or fork rewrote about 3.6k tokens. Cause unknown. Fork 3 then read 9,161, which would fit the plain resume having written a form of the prefix that later forks could read. I did not determine why forks 1 and 2 missed it.
- On a subscription the main-conversation request used the 1h TTL (all writes were `ephemeral_1h`), as documented.

Limits: n=1, one model, no tools, tiny context. Treat it as "reuse is real but not guaranteed to be total". Re-run with a realistic context before tuning anything. Raw JSON is not committed.

## What this means for the sidekick design

Each point is backed by a row above.

1. **Twin sidekicks (forks of the main session) can share the cache on Claude Code.** The mechanism is a copy of the history on the same model, with an identical tool array and system prompt. The product must not change tools, model, fast mode or thinking settings on a twin (rows 11, 13). Via ACP this means the unstable `session/fork` on `claude-agent-acp`, or Claude Code's own fork subagents.
2. **Set `subagentPromptCacheTtl` to `1h` for twins.** Forks are in the "everything else" bucket, so they default to 5 minutes even on a subscription. A fork that sits idle past 5 minutes pays a full re-read of the inherited history (row 10).
3. **Stagger sibling spawns by one response, do not fire them in the same instant.** Claude Code does this itself in workflows with a 5 second hold (rows 8, 22).
4. **Specialist or resident sidekicks with their own profile prompt share a cache only with siblings of the same profile**, not with the parent (rows 7, 8).
5. **Cache scope for a subscription account is undocumented.** Test any cross-account claim before putting it in the spec. The base run in the experiment reading 3,262 tokens it never wrote suggests prefix reuse across sessions on one login.
6. **Codex and OpenCode:** Codex derives its key from the session id and gives internal subagents a parent-derived key (row 16). A prediction-mode fork is explicitly built to maximize cache reuse (row 17). ACP fork is a capability flag with no cache contract (rows 20, 21), so the adapter matrix should record cache sharing separately from fork support.
7. **Do not quote the 37k or "30% of a window" figures in the spec as facts.** Quote the mechanism (a normal subagent builds its own prefix) and measure the product's own numbers (map note on baseline and measurement).

## Not covered

- OpenCode's own caching and session-fork behaviour (the session used OpenCode as the host, not as a harness under study).
- Whether cache reads count toward Pro and Max window limits, and by how much. Anthropic does not document the formula.
- How a subscription login maps to an API workspace for cache isolation.
- Codex fork cache behaviour outside the experimental prediction mode.
- A cold-start measurement of a real subagent in a real project. Only the single community number exists.
